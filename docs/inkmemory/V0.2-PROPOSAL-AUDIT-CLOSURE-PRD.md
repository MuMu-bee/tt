# 墨忆台 V0.2 Proposal and Audit Closure 增量 PRD

> 版本：V0.2 增量收口（Proposal/Audit Closure）  
> 状态：待架构设计与实现  
> 基线分支：`feat/memory-workbench-foundation`  
> 事实源：Vault Markdown；Proposal、Approval、Audit 和索引均为可恢复/可重建的派生记录。

## 1. 项目信息

- **Language**：简体中文
- **Programming Language**：Vite + React + MUI + Tailwind CSS（本仓库实际为 Obsidian TypeScript 插件；实现必须沿用现有 Obsidian API、TypeScript 和构建链，不引入第二套 UI 外壳）
- **Project Name**：`v02_proposal_audit_closure`
- **原始需求复述**：在现有 V0.2 混合检索、白名单整理、Hash 冲突防护、WriteService、结构化审计和 Dashboard 基础上，补齐 Proposal/Audit 的最小可用闭环：proposal 可保存和恢复，用户可逐条审批或拒绝，审批后安全 apply，失败可见且可恢复，审计可持久化查询，并提供不破坏现有 Dashboard 的最小 UI 入口。

## 2. 当前状态：已具备与缺口

### 2.1 已具备（不得回退）

- Vault Markdown 作为唯一事实源；索引为可重建派生数据。
- 关键词优先、semantic fallback、路径去重、scope/excludes（excludes 优先）契约及测试。
- `OrganizeService` 四类白名单动作：`frontmatter-add`、`tag-add`、`bidirectional-link-add`、`format-normalize`；已生成真实 `before/after/diff`。
- fiction/unknown 的 `proposal_only` 策略、默认关闭的新写入开关、目录范围快照。
- `WriteService -> WritePort -> ObsidianWritePort` 读、Hash 校验、写后 Hash、索引 refresh 状态和结构化 `request_id` 审计事件。
- 索引重建失败保留旧索引；全量与增量生命周期已有全局队列；Dashboard 搜索已有 version guard。
- Obsidian 插件壳、Dashboard、侧边栏、旧命令和打开原文路径保持兼容。
- 现有测试、TypeScript/build/lint 基线和 Hermes/终端依赖边界。

### 2.2 本增量必须补齐的缺口（P0）

1. **Proposal 持久化**：当前 `OrganizePlan/PlannedChange` 仅存在内存，缺少稳定 `proposal_id`、恢复、状态迁移和重启加载。
2. **Approval 记录**：缺少单条审批/拒绝记录，不能证明“用户明确批准了哪个版本的变更”。
3. **Apply 入口与门禁**：`WriteService` 尚无 proposal 驱动入口，必须禁止绕过 proposal/approval 直接 apply 高风险或 proposal-only 变更。
4. **Audit 持久化**：当前运行时为内存 `AuditSink`，缺少 Vault 受保护目录与独立本地目录的双写、查询、失败状态和启动恢复。
5. **失败恢复**：缺少 `pending-compensation`、待补偿队列、审计/索引失败重试、重启后恢复和明确错误状态。
6. **最小 UI 入口**：Dashboard 无 proposal 队列、diff、审批/拒绝、冲突和审计状态入口。

### 2.3 已知限制（本增量不扩大范围）

- `ObsidianWritePort` 使用 Obsidian Vault API；平台级 fsync/rename 能力受 Obsidian API 限制，必须保留 Hash 冲突防护并在文档中明确写入语义。
- semantic adapter、后台研究、Hermes 适配器仍可用不可用占位实现；本增量不以其可用为前提。

## 3. 产品目标

1. **可追溯**：每个待审批变更都有不可变 proposal 内容、目标文件、base hash、diff、原因、request_id 和生命周期状态。
2. **不可越权**：只有状态正确、单条审批有效、范围/动作白名单有效且当前文件 Hash 未变化时才能 apply；fiction/unknown 默认永不自动 apply。
3. **可恢复**：插件重启后可恢复 pending proposal、已记录 approval、apply 结果、审计记录和双写补偿任务；任何一端失败都不能伪报成功。

## 4. 用户故事

- As a 知识工作者, I want 查看某条整理 proposal 的 diff 和原因, so that 我能在写入前确认系统具体要改什么。
- As a 用户, I want 单条 approve 或 reject proposal, so that 我能对每个文件做明确授权并保留责任记录。
- As a 用户, I want 文件被外部修改后 apply 自动变为 conflict 且原文不变, so that 系统不会覆盖我的新内容。
- As a 用户, I want 在 Dashboard 查询 proposal/audit 状态并看到待补偿项, so that 我能知道失败是否需要重试。
- As a 维护者, I want 插件重启后恢复待审批和待补偿记录, so that 未完成工作不会静默丢失。

## 5. 数据与状态规范

### 5.1 ProposalStore

ProposalStore 必须提供：

```ts
interface ProposalStore {
  save(proposal: Proposal, context: RequestContext): Promise<void>;
  get(proposalId: string, context: RequestContext): Promise<Proposal | null>;
  list(filter: ProposalFilter, context: RequestContext): Promise<Proposal[]>;
  updateStatus(proposalId: string, status: ProposalStatus, context: RequestContext): Promise<void>;
}
```

最小数据字段：

- `proposal_id`、`request_id`、`target_path`、`target_zone`
- `change_kind`（仅四类白名单动作）
- `base_hash`、`before`/`after` 或可重放 patch、`diff`
- `reason`、可选 `model/provider`
- `created_at`、可选 `expires_at`
- `status`、`requires_approval`、`schema_version`

状态：`pending` → `approved` / `rejected`；approved → `applied` / `conflict` / `failed` / `expired`；任何双写或审计未完成可关联 `pending-compensation`。终态不得被普通更新覆盖；重试必须产生新的审计事件，不能伪造成功。

### 5.2 ApprovalStore

本轮至少支持单条审批；接口和数据模型应为未来批量审批保留扩展位：

```ts
interface ApprovalRecord {
  approval_id: string;
  proposal_id: string;
  request_id: string;
  decision: 'approve' | 'reject';
  actor: 'user';
  decided_at: string;
  note?: string;
}
```

同一 proposal 只允许一个有效最终决策；重复点击必须幂等返回已有决策，不得重复 apply。reject 只更新状态并写审计，不触碰目标文件。

### 5.3 AuditStore

AuditStore 必须支持双端写入和查询：

```ts
interface AuditStore {
  append(event: WriteAudit | ApprovalAudit, context: RequestContext): Promise<AuditWriteStatus>;
  query(filter: AuditFilter, context: RequestContext): Promise<AuditRecord[]>;
  listPendingCompensation(context: RequestContext): Promise<AuditRecord[]>;
  retry(recordId: string, context: RequestContext): Promise<AuditWriteStatus>;
}
```

审计字段至少包括：`audit_id`、`request_id`、`proposal_id`、`target_path`、`action`、`actor`、`before_hash`、`after_hash`、`result`、`error_code`、`created_at`、内容 hash。写入审计结果枚举至少为：`success`、`conflict`、`failed`、`pending-compensation`。

持久化位置：

- Vault：`_workbench/proposals/`、`_workbench/approvals/`、`_workbench/audit/`（受保护目录，不能进入普通整理扫描）。
- 独立本地目录：插件数据目录下对应 `proposals/`、`approvals/`、`audit/`。

两端记录必须共享 `request_id` 和内容 hash；任一端成功、另一端失败时必须返回 `pending-compensation`，并保留已成功端内容。

## 6. 核心流程与安全验收

### 6.1 生成 Proposal

1. `OrganizeService.plan` 生成变更；每个文件单独生成 proposal。
2. Proposal 保存前复核 path、zone、scope snapshot、change kind 和 base hash。
3. fiction/unknown 只能为 `pending + requires_approval=true`；不得生成可直接 apply 的路径。
4. 保存 ProposalStore 双端记录并写 `proposal-created` 审计；任一端失败进入 `pending-compensation`。

### 6.2 单条审批

1. UI 读取 proposal 详情和 diff；用户明确点击 approve/reject。
2. ApprovalStore 保存 `ApprovalRecord`，使用独立 request context 并关联原 proposal request_id。
3. approve 仅允许 `pending` 且未过期 proposal；reject 仅允许 `pending`。
4. 审批后更新 proposal 状态并写审计；重复操作幂等，状态不允许倒退。

### 6.3 Apply

审批 apply 必须按以下顺序执行：

1. 读取 proposal，确认存在、状态为 `approved`、未过期、未被拒绝/已应用。
2. 重新校验目标 path、scope、zone、白名单动作和 `requires_approval`。
3. 通过 `WritePort.read` 计算当前 hash，与 `base_hash` 比较；不一致则 `conflict`，零写入、零覆盖。
4. 使用 `WriteService` 执行写入；禁止 UI、Dashboard 或其他服务直接调用 Vault 写入。
5. 写后重新读取并计算 `after_hash`；触发索引 refresh，状态必须可见。
6. 写入 ProposalStore 状态和 AuditStore 双端审计；只有写入、索引状态和审计要求均满足才可显示 `applied/success`。

**安全验收必须包含：**

- feature flag 关闭时零写入、零 proposal apply。
- 白名单外动作被拒绝。
- fiction/unknown 自动 apply 被拒绝并保持 proposal-only。
- stale hash apply 返回 `conflict`，目标原文和 hash 不变。
- rejected、expired、already-applied、duplicate approval 不能写入。
- 单条 apply 失败不会影响其他 proposal。
- 所有 apply/approval/proposal 事件含 request_id、actor、path 和前后 hash（如适用）。

## 7. 失败恢复与一致性

- **Vault 写入失败**：目标文件保持原文；proposal 标为 `failed`，写失败审计；不得报告 applied。
- **索引 refresh 失败**：文件写入结果保留，但 proposal/audit 标注 `applied-index-pending` 或等价失败状态，提供重试入口。
- **审计双写失败**：返回 `pending-compensation`；UI 展示缺失端、错误码和重试按钮；不得静默吞错。
- **Proposal/Approval 双写失败**：保留成功端，启动时按内容 hash 补偿缺失端；冲突时生成冲突记录，不删除任一端。
- **插件重启**：初始化时加载 pending proposal、approved 未 apply、pending-compensation 和失败记录；恢复过程不自动写 Vault，需用户继续确认或显式重试。
- **重复重试**：以 `proposal_id + operation` 做幂等约束；重复审计不得改变历史结果。
- **回滚**：本轮至少保存 before/after hash 和原文快照或 patch 数据结构；实际回滚 UI 可延后，但不得覆盖 apply 后已发生变化的文件，hash 不一致必须转 conflict。

## 8. UI 最小入口

沿用现有 `AgentDashboardView`，不新建并行外壳；新增一个最小“整理审批”区域即可：

1. **状态卡**：待审批数量、冲突数量、失败数量、待补偿数量、最近一次同步状态。
2. **Proposal 列表**：显示目标路径、动作、zone、创建时间、状态和 request_id 短标识。
3. **单条详情**：显示 before/after、diff、base hash、过期时间、原因；敏感正文仅按现有最小片段策略展示。
4. **操作**：`批准并应用`、`拒绝`、`重试补偿`；按钮根据状态禁用，必须给出 Notice/状态文案。
5. **结果反馈**：success、conflict、failed、pending-compensation 均明确显示；冲突必须提供“重新生成 proposal”提示。
6. **审计查询最小筛选**：优先支持 `request_id`、文件路径和结果；完整时间/动作/操作者筛选可保留为后续增强，但底层接口应可扩展。

UI 不得直接读写 Vault 或绕过服务层；旧搜索、打开原文、Dashboard 刷新行为不得回归。

## 9. 测试与 CI 验收

### 9.1 必测用例（P0）

- Proposal 双端保存、读取、状态迁移和重启恢复。
- 单条 approve/reject；重复点击幂等；过期/非 pending 拒绝。
- approved proposal apply 成功，验证 before/after hash、索引 refresh 和审计关联。
- stale hash conflict 零写入；fiction/unknown proposal-only。
- 写入失败、索引刷新失败、审计一端失败、两端不一致的状态与补偿。
- 启动加载 pending-compensation；重试成功后状态清除并保留历史审计。
- 路径穿越、非 Markdown 路径、白名单外 change kind、scope/excludes 逃逸均被拒绝。
- Dashboard 最小点击流：查看 diff → approve/reject → 显示结果；旧搜索→打开原文通过。

必须通过：

```text
npx tsc --noEmit

```

同时将 Proposal/Audit 专项测试纳入 `npm test` 和 GitHub Actions；CI 不得只执行 build/lint。新增测试不得依赖真实 Hermes CLI、终端、`child_process` 或网络服务。移动端兼容和真实 Obsidian 桌面 smoke test 若当前环境不可用，必须作为明确的已知限制记录，不得冒充已验收。

## 10. 优先级与实施边界

- ProposalStore、ApprovalStore、AuditStore 最小端口与内存/本地可测试 adapter。
- Proposal/Approval/Audit 数据模型、状态机、双写失败状态。
- 单条审批、apply 门禁、Hash 冲突、白名单、proposal-only。
- 重启恢复与 pending-compensation 重试。
- Dashboard 最小审批/审计状态入口。
- 单元/集成测试接入 npm test 和 CI。

### P1（本轮可做但不得阻塞 P0）

- 审计按路径、request_id、结果筛选。
- apply 前后快照/patch 保存及只读回滚准备。
- 更清晰的索引 refresh pending 展示。

### P2（后续）

- 批量审批、批量 apply、完整审计报表。
- 审计冲突可视化和管理员修复工具。

## 11. 明确不做事项

- 不改变 Vault Markdown 为事实源的原则，不把 Proposal/Audit Store 当作原文事实源。
- 不接入 Hermes CLI、`child_process`、`spawn`、shell 或 terminal 执行能力。
- 不在本轮实现后台联网研究、embedding provider、Hermes 发布/同步、动态记忆版本管理。
- 不实现无审批的高风险改写、正文语义重写、删除、移动、批量自动 apply。
- 不取消 fiction/unknown proposal-only 保护，不允许模型扩大 scope 或白名单。
- 不新建并行 Dashboard/React 外壳，不破坏旧命令、侧边栏、搜索和打开原文闭环。
- 不承诺平台级 fsync/rename 超出 Obsidian API 的能力；不以“写入成功”掩盖索引或审计失败。
- 不修改 `.workbuddy/`、`overview.md`，不在本 PRD 阶段 commit、push 或 merge。
